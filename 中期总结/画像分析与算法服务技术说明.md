## 二、画像分析系统

### 2.1 数据计算原理

画像分析系统基于工作量明细数据，通过Python算法服务自动计算员工的多维度能力得分。系统支持三种画像类型，每种画像关注不同的能力维度。

#### 2.1.1 能力画像（Ability Image）

能力画像评估员工的基础工作能力，包含三个核心维度：

**1. 技术能力（Tech Ability）**

计算公式：
```
tech_ability = max(0, min(100, (avg_task_weight - 0.5) / 1.5 * 100))
```

- **数据来源**: `biz_workload_detail`表中的`task_weight`字段平均值
- **计算逻辑**: 将任务难度权重（范围0.5-2.0）线性映射到0-100分
- **业务含义**: 难度权重越高，说明员工处理的技术难度越大，技术能力越强

**2. 工作量能力（Workload Ability）**

计算公式：
```
workload_ability = min(100, min(50, (total_hours / 160) * 50) + min(50, (total_records / 30) * 50))
```

- **数据来源**: 
  - `total_hours`: 总工时数（`SUM(time_spent_hrs)`）
  - `total_records`: 总任务记录数（`COUNT(*)`）
- **计算逻辑**: 
  - 工时维度：标准值160小时（约1个月），满分50分
  - 任务数维度：标准值30条记录，满分50分
  - 两者相加，最高100分
- **业务含义**: 综合考虑工时总量和任务数量，评估员工的工作量承载能力

**3. 稳定性能力（Stability Ability）**

计算公式：
```
mean = sum(quality_scores) / len(quality_scores)
std_dev = sqrt(sum((x - mean)²) / len(quality_scores))
stability_ability = max(0, min(100, 100 - (std_dev * 20)))
```

- **数据来源**: `biz_workload_detail`表中的`quality_score`历史序列
- **计算逻辑**: 
  - 计算质量评分的标准差
  - 标准差越大，稳定性得分越低
  - 数据不足时返回75分（默认稳定）
- **业务含义**: 通过质量评分的波动性评估工作稳定性，波动越小稳定性越高

**能力画像综合得分**：
```
ability_score = tech_ability * 0.4 + workload_ability * 0.4 + stability_ability * 0.2
```

权重分配：技术40%、工作量40%、稳定性20%

#### 2.1.2 绩效画像（Performance Image）

绩效画像评估员工的工作质量和业绩贡献，包含三个核心维度：

**1. 质量能力（Quality Ability）**

计算公式：
```
quality_ability = min(100, max(0, avg_quality_score * 100))
```

- **数据来源**: `biz_workload_detail`表中的`quality_score`平均值
- **计算逻辑**: 将平均质量评分（0-1）直接转换为0-100分
- **业务含义**: 反映员工的工作质量水平

**2. 贡献能力（Contribution Ability）**

计算公式：
```
eci_score = SUM(time_spent_hrs * task_weight * quality_score)
contribution_ability = min(100, (eci_score / 1000) * 100)
```

- **数据来源**: ECI（效率贡献指数）计算
- **ECI计算公式**: `ECI = 工时 × 任务权重 × 质量评分`
- **计算逻辑**: 将ECI得分（基准值1000）映射到0-100分
- **业务含义**: 综合考虑工时、难度、质量，反映员工的综合贡献水平

**3. 绩效趋势（Performance Trend）**

计算公式：
```
performance_trend = (quality_scores[-1] - quality_scores[0]) / len(quality_scores) * 100
```

- **数据来源**: 质量评分历史序列的首尾差值
- **计算逻辑**: 
  - 正值表示上升趋势，负值表示下降趋势
  - 单位：百分比
- **业务含义**: 评估员工质量表现的近期变化趋势

**绩效画像综合得分**：
```
performance_score = quality * 0.5 + contribution * 0.4 + ((trend + 100) / 2) * 0.1
```

权重分配：质量50%、贡献40%、趋势10%

#### 2.1.3 潜力画像（Potential Image）

潜力画像评估员工的未来发展潜力和晋升可能性，包含四个核心维度：

**1. 学习能力（Learning Ability）**

计算公式：
```
trend = (task_weights[-1] - task_weights[0]) / len(task_weights) * 100
learning_ability = min(100, max(0, 50 + trend * 10))
```

- **数据来源**: 任务难度权重历史序列
- **计算逻辑**: 
  - 基础分50分
  - 根据任务难度上升趋势调整（趋势×10）
- **业务含义**: 任务难度提升越快，学习能力越强

**2. 成长速度（Growth Speed）**

计算公式：
```
trend = (quality_scores[-1] - quality_scores[0]) / len(quality_scores) * 100
growth_speed = min(100, max(0, 50 + trend * 50))
```

- **数据来源**: 质量评分历史序列
- **计算逻辑**: 
  - 基础分50分
  - 根据质量提升趋势调整（趋势×50，系数更大）
- **业务含义**: 质量提升越快，成长速度越快

**3. 激励响应（Incentive Response）**

计算公式（皮尔逊相关系数）：
```
mean_points = sum(points_data) / len(points_data)
mean_quality = sum(quality_data) / len(quality_data)
numerator = sum((points_data[i] - mean_points) * (quality_data[i] - mean_quality))
denom_p = sqrt(sum((p - mean_points)²))
denom_q = sqrt(sum((q - mean_quality)²))
correlation = numerator / (denom_p * denom_q)
incentive_response = max(0, min(100, (correlation + 1) / 2 * 100))
```

- **数据来源**: 积分历史序列和质量评分历史序列
- **计算逻辑**: 
  - 计算积分与质量评分的皮尔逊相关系数（-1到1）
  - 将相关系数映射到0-100分（(correlation + 1) / 2 * 100）
- **业务含义**: 相关性越高，说明员工对激励的响应越强

**4. 晋升概率（Promotion Probability）**

计算公式：
```
base_ability = (tech_ability + quality_ability) / 2
potential_score = learning_ability * 0.3 + growth_speed * 0.3 + incentive_response * 0.2 + base_ability * 0.2
promotion_probability = min(0.95, max(0.1, potential_score / 100))
```

- **计算逻辑**: 
  - 潜力得分权重：学习能力30%、成长速度30%、激励响应20%、基础能力20%
  - 晋升概率 = 潜力得分 / 100，限制在0.1-0.95之间
- **业务含义**: 综合评估员工的晋升可能性

**潜力画像综合得分**：
```
potential_score = learning_ability * 0.3 + growth_speed * 0.3 + incentive_response * 0.2 + base_ability * 0.2
```

## 三、工作量管理系统

### 3.1 ECI（效率贡献指数）计算公式

**核心公式**：
```
ECI = SUM(time_spent_hrs * task_weight * quality_score)
```

- **`time_spent_hrs`**: 工时数（小时）
- **`task_weight`**: 任务难度权重（0.5-2.0）
- **`quality_score`**: 质量评分（0-1，对应1-5星）

**业务含义**: ECI综合考虑工时、难度、质量三个维度，反映员工的综合贡献水平。ECI值越高，说明员工在相同时间内完成了更多高质量、高难度的工作。

### 3.2 统计数据计算

**后端SQL实现**（`WorkloadDetailMapper.xml`）：

```sql
SELECT 
    COUNT(*) as task_count,
    COALESCE(SUM(time_spent_hrs), 0) as total_hours,
    COALESCE(AVG(task_weight), 0) as avg_task_weight,
    COALESCE(AVG(quality_score), 0) as avg_quality,
    COALESCE(SUM(time_spent_hrs * task_weight * quality_score), 0) as eci_score
FROM biz_workload_detail
WHERE 1=1
    AND staff_id = #{staffId}  -- 可选
    AND project_id = #{projectId}  -- 可选
    AND work_date >= #{startDate}  -- 可选
    AND work_date <= #{endDate}  -- 可选
```

**关键指标**：

1. **总工时（total_hours）**: `SUM(time_spent_hrs)`
2. **任务数量（task_count）**: `COUNT(*)`
3. **平均难度（avg_task_weight）**: `AVG(task_weight)`
4. **平均质量（avg_quality）**: `AVG(quality_score)`
5. **ECI得分（eci_score）**: `SUM(time_spent_hrs * task_weight * quality_score)`

## 四、人员匹配优化系统

### 4.1 技能标签识别

**核心函数**：`_normalize_tags(tags_str)`（`app.py`第639-649行）

```python
def _normalize_tags(tags_str):
    """
    将技能/标签字符串统一转为小写，按常见分隔符拆分，去除空白。
    支持分隔符：逗号(, ，)、顿号(、)、分号(;)、空格。
    """
    if not tags_str:
        return set()
    # 统一分隔符为逗号
    for sep in ['，', '、', ';', '；', ' ']:
        tags_str = tags_str.replace(sep, ',')
    return set([s.strip().lower() for s in tags_str.split(',') if s.strip()])
```

**技能匹配度计算**：

```python
def calculate_skill_match(employee_skills, project_skills):
    if not project_skills:
        return 1.0  # 项目未要求技能，视为全匹配
    emp_set = _normalize_tags(employee_skills)
    proj_set = _normalize_tags(project_skills)
    if not proj_set:
        return 1.0
    intersection = emp_set & proj_set
    return len(intersection) / len(proj_set)  # 匹配度 = 交集 / 项目需求数
```

**业务逻辑**：
- 支持多种分隔符（逗号、顿号、分号、空格）
- 统一转为小写，去除空白
- 匹配度 = 员工技能与项目需求技能的交集数 / 项目需求技能总数

### 4.2 Gurobi优化模型

**核心函数**：`optimize_staff_allocation(project_data, employees_data)`（`app.py`第685-931行）

#### 4.2.1 决策变量

```python
x[staff_id] = model.addVar(vtype=GRB.BINARY, name=f"assign_{staff_id}")  # 员工是否被选中（0/1）
y[staff_id] = model.addVar(lb=0, ub=max_individual_hours, vtype=GRB.CONTINUOUS, name=f"hours_{staff_id}")  # 分配给员工的工时
```

- **`x[staff_id]`**: 二进制变量，表示员工是否被选中参与项目
- **`y[staff_id]`**: 连续变量，表示分配给该员工的工时数

#### 4.2.2 目标函数

```python
model.setObjective(
    sum(total_scores[staff_id] * y[staff_id] for staff_id in staff_ids), 
    GRB.MAXIMIZE
)
```

**目标**: 最大化 `总得分 × 分配工时`

- **`total_scores[staff_id]`**: 员工综合得分（技能匹配70% + 质量15% + 能力15%）
- **业务含义**: 确保能力高、技能匹配的员工分配更多工时

#### 4.2.3 评分机制

**技能匹配员工**：
```python
total_score = match_score * 0.7 + quality_weight * 0.15 + ability_weight * 0.15
```

**技能不匹配员工**：
```python
total_score = quality_weight * 0.1 + ability_weight * 0.1
```

**权重分配**：
- 技能匹配：技能70%、质量15%、能力15%
- 技能不匹配：质量10%、能力10%（降权处理，但仍能区分能力差异）

#### 4.2.4 约束条件

**约束1：员工数量上限**
```python
max_assignable_staff = min(max_staff_count, len(staff_ids))
model.addConstr(sum(x[staff_id] for staff_id in staff_ids) <= max_assignable_staff, "max_staff")
```

**约束2：总工时预算**
```python
total_capacity = sum(max_hours_dict[sid] for sid in staff_ids)
if total_capacity >= budgeted_hours * 0.8:
    # 容量充足，要求总工时精确等于预算
    model.addConstr(sum(y[staff_id] for staff_id in staff_ids) == budgeted_hours, "budget")
else:
    # 容量不足，尽力分配
    model.addConstr(sum(y[staff_id] for staff_id in staff_ids) <= budgeted_hours, "budget")
```

**约束3：员工工时与选中状态关联**
```python
min_hours_each = budgeted_hours / max_staff_count * 0.3  # 选中后至少30%的人均工时
for staff_id in staff_ids:
    model.addConstr(y[staff_id] <= max_hours_dict[staff_id] * x[staff_id], f"link_max_{staff_id}")
    model.addConstr(y[staff_id] >= min_hours_each * x[staff_id], f"link_min_{staff_id}")
```

**动态工时上限计算**：
```python
avg_hours = budgeted_hours / max_staff_count
max_individual_hours = min(budgeted_hours, avg_hours * 1.5)  # 人均工时的1.5倍封顶
max_individual_hours = max(1, max_individual_hours)  # 至少1小时
```

#### 4.2.5 故障容错机制

当Gurobi求解失败（INFEASIBLE）时，使用贪心算法作为备选方案：

```python
if model.status == 3:  # INFEASIBLE
    # 按得分排序，选择前max_staff_count个员工
    sorted_staff = sorted(staff_ids, key=lambda sid: total_scores[sid], reverse=True)[:max_assignable]
    total_score_sum = sum(total_scores[sid] for sid in sorted_staff)
    # 按得分比例分配工时
    for staff_id in sorted_staff:
        allocated_hours = budgeted_hours * (total_scores[staff_id] / total_score_sum)
```

## 七、关键问题与解决方案

### 7.1 画像分析数据为空问题

**问题描述**: 画像分析时，`quality_scores`和`task_weight_history`数组为空，导致趋势分析失败。

**根本原因**: 
- `WorkloadDetailMapper.xml`中的`selectWorkloadStatsByStaffId`查询使用了`GROUP_CONCAT`，但MyBatis返回的是字节数组而不是字符串

**解决方案**:
1. 在SQL中使用`CAST(GROUP_CONCAT(...) AS CHAR)`确保返回字符串
2. 前端使用`parseStringToArray`函数将逗号分隔字符串解析为数组

**相关代码**:
```sql
CAST(GROUP_CONCAT(quality_score ORDER BY work_date ASC) AS CHAR) as quality_scores_str
```

```javascript
const parseStringToArray = (str) => {
  if (!str) return []
  return str.split(',').map(v => parseFloat(v)).filter(v => !isNaN(v))
}
```

### 7.2 技能标签识别不准确问题

**问题描述**: 员工技能标签与项目需求技能匹配时，即使员工有相关技能，匹配度仍为0。

**根本原因**: 
- 技能字符串格式不统一（逗号、顿号、分号、空格混用）
- 大小写不一致
- 空白字符干扰

**解决方案**:
1. 实现`_normalize_tags`函数，统一处理各种分隔符
2. 统一转为小写，去除空白
3. 使用集合交集计算匹配度

**相关代码**:
```python
def _normalize_tags(tags_str):
    if not tags_str:
        return set()
    for sep in ['，', '、', ';', '；', ' ']:
        tags_str = tags_str.replace(sep, ',')
    return set([s.strip().lower() for s in tags_str.split(',') if s.strip()])
```

### 7.3 Gurobi优化结果不合理问题

**问题描述**: 
- 所有员工分配工时相同
- 只分配给一个员工
- 总工时不等于项目预算

**根本原因**:
1. 目标函数设置不合理（最初是最大化总得分，导致能力高的员工被选中但工时分配不均）
2. 工时上限计算不合理（固定值，未考虑项目预算和员工能力）
3. 约束条件过于严格（固定10小时最低分配，导致小项目无法分配）

**解决方案**:
1. **修改目标函数**: 从`maximize(sum(total_scores))`改为`maximize(sum(total_scores * hours))`，确保能力高的员工分配更多工时
2. **动态工时上限**: `max_individual_hours = min(budgeted_hours, avg_hours * 1.5)`，按人均工时的1.5倍封顶
3. **动态最低分配**: `min_hours_each = budgeted_hours / max_staff_count * 0.3`，按项目预算动态计算
4. **灵活总工时约束**: 容量充足时精确等于预算，容量不足时尽力分配

**相关代码**:
```python
# 目标函数
model.setObjective(
    sum(total_scores[staff_id] * y[staff_id] for staff_id in staff_ids), 
    GRB.MAXIMIZE
)

# 动态工时上限
avg_hours = budgeted_hours / max_staff_count
max_individual_hours = min(budgeted_hours, avg_hours * 1.5)

# 动态最低分配
min_hours_each = budgeted_hours / max_staff_count * 0.3
```

### 7.4 前端数据展示错误问题

**问题描述**: 
- 平均质量评分显示为1星，但实际是5星
- ECI贡献在"画像分析"和"工作量明细"页面不一致

**根本原因**:
1. `el-rate`组件期望0-5的值，但后端返回的是0-1的值
2. "画像分析"使用精确的`SUM(h*w*q)`，而"工作量明细"使用近似的`totalHours * avgTaskWeight * avgQuality`

**解决方案**:
1. 前端显示时乘以5：`(statistics.avgQuality || 0) * 5`
2. 修改`selectStatistics`查询，直接计算`SUM(h*w*q)`作为`eci_score`，确保一致性

**相关代码**:
```vue
<el-rate :model-value="(statistics.avgQuality || 0) * 5" disabled />
```

```sql
COALESCE(SUM(time_spent_hrs * task_weight * quality_score), 0) as eci_score
```

### 7.7 技能标签显示为空问题

**问题描述**: 画像管理页面中，技能标签列显示为空。

**根本原因**: 
- `hr_emp_image.skill_tags`字段经常为空
- `hr_employee.skill_tags`字段也经常为空

**解决方案**: 在SQL查询中使用三层`COALESCE`，优先使用画像中的标签，其次使用员工信息中的标签，最后从项目需求中推断：

```sql
COALESCE(ei.skill_tags, s.skill_tags, 
    (SELECT CAST(GROUP_CONCAT(DISTINCT tp.required_skills SEPARATOR ',') AS CHAR)
     FROM biz_workload_detail wd
     LEFT JOIN biz_task_project tp ON wd.project_id = tp.id
     WHERE wd.staff_id = ei.staff_id
     LIMIT 1)
) as skill_tags
```
